# 0001 版本新舊的判斷順序

- 狀態：accepted（2026-10-16）

## 背景

AGENTS.md 規定：同一個 id 有多個版本時，以 `meta.lastUpdated` 取最新，相同時再比批次序號。

實際檢查 Synthea 的輸出後發現，Patient、Encounter、Condition、Observation 共 683,514 筆，**沒有任何一筆有 `meta.lastUpdated`**，也沒有 `meta.versionId`；`meta` 裡只有 `profile`。照原本的規則，第一步永遠比不出結果。

另外，同一批裡也可能出現同一個 id 兩次，這時批次序號也相同，需要第三個比較條件，結果才會固定。

## 選項

**`lastUpdated` 缺值時怎麼辦：**

- **A. 用批次的時間補上**：有效更新時間 = `meta.lastUpdated`，缺值時用所屬批次的某個時間；接著比批次序號；最後比檔案中的行號。
- **B. 只比批次序號**：不看 `lastUpdated`。
- **C. 產資料後自己補上 `lastUpdated`**：替每筆資料寫入假的時間。

**選 A 的話，用批次的哪一個時間：**

- **實際執行時間**：Synthea metadata 的 `runStartTime`，也就是產生這批資料的時刻。
- **資料截止日**：Synthea metadata 的 `endTime`，也就是這批資料模擬到哪一天（等於 `-e` 參數）。

## 決定

選 A，用**資料截止日**。版本的比較鍵是 **（有效更新時間, 批次序號, 行號）**，三者依序比較，大者為新。

- 有效更新時間 = `meta.lastUpdated`；缺值時，用所屬批次的資料截止日，以當天 00:00 UTC 表示。
- 這只是為了和 `lastUpdated` 放在同一個欄位比較而定的寫法，不代表資料在那一刻被更新。

### 資料截止日是批次層級的時間

資料截止日描述的是**整個批次**：「這一批是來源系統在哪一天的樣子」。同一批裡的每一筆資料都拿到同一個值，**它不是每筆資料各自的更新時間**。

所以：

- 它只能用來比較**不同批次**的版本誰新誰舊，不能用來判斷某一筆資料是什麼時候被修改的。
- 某筆資料在 `batch_002` 和 `batch_003` 內容完全相同時，它的有效更新時間仍然會不同。判斷「內容有沒有變」要看內容雜湊值（ADR-0005），不能看有效更新時間。
- 同一批內的先後，靠的是第三個比較條件「行號」，不是有效更新時間。

## 理由

- 保留 AGENTS.md 的原意，以後接上真正會帶 `lastUpdated` 的 FHIR 來源，不用改規則。
- 在 Synthea 資料上，效果等於「模擬日期較晚的批次贏」，符合直覺。
- **用資料截止日，而不是實際執行時間**：每一批都是獨立執行的（ADR-0002），可以用任何順序產生。如果只重新產生 `batch_002`，它的實際執行時間會比 `batch_004` 晚，管線就會誤以為 `batch_002` 比較新。資料截止日只取決於 `-e` 參數，和什麼時候執行無關。
- 之前在快照做法中觀察到 `endTime` 不可靠（某一批跳回 `20180614`）；改用 `-e` 做法後實測，`endTime` 等於 `-e` 的值。
- B 違反 AGENTS.md，而且遇到真實資料「晚到的舊版本」時會判斷錯。
- C 會讓 Bronze 不再是原樣，違反 Bronze 的定位（ADR-0003）。

## 後果

- 完整的 Synthea 資料測不到「`lastUpdated` 不同」的情況，必須用 `tests/fixtures/` 的手工資料測，包括「晚到的舊版本不能蓋掉新版本」。
- 登記批次時要檢查 metadata 的 `endTime` 存在，而且格式是 `YYYYMMDD`，否則該批失敗。
- 行號必須能穩定取得，Bronze 要保存每一筆在來源檔中的行號。
