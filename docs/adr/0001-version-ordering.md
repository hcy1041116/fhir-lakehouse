# 0001 版本新舊的判斷順序

- 狀態：accepted（2026-10-16，2026-10-17 修訂：`lastUpdated` 改由匯出模擬器提供）

## 背景

AGENTS.md 規定：同一個 id 有多個版本時，以 `meta.lastUpdated` 取最新，相同時再比批次序號。

實際檢查 Synthea 的輸出後發現，Patient、Encounter、Condition、Observation 共 683,514 筆，**沒有任何一筆有 `meta.lastUpdated`**，也沒有 `meta.versionId`；`meta` 裡只有 `profile`。照原本的規則，第一步永遠比不出結果。

另外，同一批裡也可能出現同一個 id 兩次，這時批次序號也相同，需要第三個比較條件，結果才會固定。

## 選項

**`lastUpdated` 從哪裡來：**

- **A. 管線用批次的時間補上**：有效更新時間 = `meta.lastUpdated`，缺值時由管線用所屬批次的時間代替。
- **B. 只比批次序號**：不看 `lastUpdated`。
- **C. 由來源提供**：讓資料在進入管線之前就帶有 `lastUpdated`。

**管線補時間時，用批次的哪一個時間：**

- **實際執行時間**：產生這批資料的時刻。
- **資料截止日**：這批資料代表哪一天的樣子。

## 決定

選 C，並保留 A 當防呆。

- `meta.lastUpdated` 由匯出模擬器在來源端補上，值為該批的資料截止日 00:00:00Z（ADR-0009）。
- 有效更新時間 = `meta.lastUpdated`；萬一缺值，用所屬批次的資料截止日（取自匯出清單的 `transactionTime`）。
- 版本的比較鍵是 **（有效更新時間, 批次序號, 行號）**，三者依序比較，大者為新。

### 有效更新時間仍然是批次層級的時間

不論是模擬器補上的 `lastUpdated`，還是缺值時的資料截止日，同一批裡每一筆有變動的資料都拿到同一個值。**它不是每筆資料各自真正的修改時間**，因為 Synthea 不會告訴我們某筆資料是在這 30 天內的哪一天改的。

所以：

- 它只能用來比較**不同批次**的版本誰新誰舊，不能用來判斷某一筆資料是什麼時候被修改的。
- 判斷「內容有沒有變」要看內容雜湊值（ADR-0005），不能看有效更新時間。
- 同一批內的先後，靠的是第三個比較條件「行號」。

## 理由

- 保留 AGENTS.md 的原意：先看 `lastUpdated`。真實的 FHIR 來源本來就會帶 `lastUpdated`，換成真實來源時不用改規則。
- **C 不違反「Bronze 原樣保存」**：最初考慮過「產資料後自己補上 `lastUpdated`」，當時否決的理由是 Bronze 就不再是原樣。現在補值的是匯出模擬器，它在管線外面、扮演來源系統；從管線的角度看，Bronze 仍然原封不動保存來源給的資料（ADR-0003、ADR-0009）。
- **保留 A 當防呆**：測試資料或未來其他來源可能沒有 `lastUpdated`，有一個明確的退路，結果才會固定。
- **用資料截止日，不用實際執行時間**：每一批都是獨立執行的（ADR-0002），可以用任何順序產生。如果只重新產生 `batch_002`，它的實際執行時間會比 `batch_004` 晚，管線就會誤以為 `batch_002` 比較新。資料截止日只取決於 `-e` 參數，和什麼時候執行無關。
- B 違反 AGENTS.md，而且遇到真實資料「晚到的舊版本」時會判斷錯。

## 後果

- 完整的 Synthea 資料中，同一批內的 `lastUpdated` 都相同，測不到「`lastUpdated` 不同、批次順序相反」的情況，必須用 `tests/fixtures/` 的手工資料測，包括「晚到的舊版本不能蓋掉新版本」，以及「`lastUpdated` 缺值時改用資料截止日」。
- 登記批次時要檢查匯出清單的 `transactionTime` 存在且格式正確，否則該批失敗。
- 行號必須能穩定取得，Bronze 要保存每一筆在來源檔中的行號。
