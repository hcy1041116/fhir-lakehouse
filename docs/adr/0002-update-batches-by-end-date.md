# 0002 更新批次用「延長模擬截止日」產生

- 狀態：accepted（2026-10-16）

## 背景

增量處理需要「同一個 id、內容不同」的多批資料，才能驗證「取最新」和「只更新有變的」。目標是 1000 人、4 個批次，模擬來源系統每月更新一次。開發環境是 WSL，記憶體 8GB。

Synthea 的 id 和每個人的人生，都是從種子推導出來的。種子、醫師種子（`-cs`）、參考日期（`-r`）都固定時，同樣的參數每次產出的內容逐字相同；沒有固定 `-cs` 的話，Encounter 的 `participant` 每次都不一樣。

## 選項

- **A. 換種子**：每批用不同的 `-s`。
- **B. 快照接續**：第一批用 `-u` 把所有病人的模擬狀態存成快照，之後每批用 `-i` 載入上一批的快照，`-t 30` 往後模擬 30 天，再存新快照。
- **C. 跑一次再切檔**：模擬到最後一個日期，再依日期把資料切成 4 批。
- **D. 延長模擬截止日**：種子和參考日期都固定，每批只把模擬截止日（`-e`）往後延 30 天，各自獨立執行。

## 實驗結果

| 選項 | 實驗 | 結果 |
|---|---|---|
| A | 3 人，`-s 42` 和 `-s 43` | 四種資源的 id **完全沒有重疊** |
| B | 6 人，連續 3 批，每批 30 天 | id 重疊、有內容改變，可行 |
| B | **1000 人**存快照 | 執行 26 分鐘只完成約 295 人，**Java 記憶體不足**，停不下來，只能強制結束 |
| D | 2 人，`-e 20261013` 和 `-e 20261112` | 出生日期不變；id 重疊；大部分內容相同；1 筆 Condition 從 `active` 變成 `resolved`，1 筆 Encounter 的結束時間更新；每次約 9 秒，記憶體約 1.2GB |

## 決定

選 D。所有批次都用 `-p 1000 -s 42 -cs 42 -r 20261013`，只有 `-e` 不同：

| 批次 | `-e` |
|---|---|
| `batch_001`（初始批次） | `20261013` |
| `batch_002` | `20261112` |
| `batch_003` | `20261212` |
| `batch_004` | `20270111` |

某個 id 在後來的批次**未出現，不視為刪除**。刪除留到第二階段，用刪除清單或 `entered-in-error` 狀態明確模擬。

## 理由

- **A 測不到版本比較**：換種子就是一群全新的病人，只會測到新增。
- **B 在這台電腦上跑不了 1000 人**：存快照時，Synthea 要把所有病人的模擬狀態一直留在記憶體裡，等全部模擬完才一起寫出去。實測 58 人就用掉約 1.9GB，1000 人遠超過 8GB。不存快照時，Synthea 模擬完一個人就寫出病歷、從記憶體丟掉，所以 1000 人只要 73 秒。
- **C 只會有最終版本**：一次模擬到最後，每筆資料只會輸出最後的樣子。例如一筆 10/1 發病、11/5 痊癒的 Condition，切檔後會帶著「11/5 痊癒」被放進 10/13 那一批，結果只能測到新增，測不到更新。
- **D 每批都是 Synthea 自己模擬到那一天的樣子**：種子固定，截止日之前的人生每次都一樣，只有截止日之後發生的事會造成差異，這正是來源系統定期更新的樣子。每一批都是一般的執行，記憶體用量和平常一樣。
- 參考日期 `-r` 決定病人的出生日期，所以四批都固定為 `20261013`；只改 `-e`，出生日期就不會跟著平移。
- Synthea 預設只匯出最近 10 年（`exporter.years_of_history = 10`），截止日往後延，最舊的資料就會掉出範圍。所以「未出現」只是匯出範圍改變，不能解讀成刪除。

## 後果

- 每一批都從每個人出生開始重新模擬，比快照做法多花 CPU，每批約 1 分多鐘。
- 不需要快照檔，原本預估的約 14GB 磁碟空間也省下來。
- 每一批都獨立執行，可以用任何順序產生或只重新產生其中一批。因此批次的時間不能用實際執行時間，要用資料截止日（ADR-0001）。
- 2 人的實驗中，30 天內沒有新增的資料；1000 人預估每批會有新增，也會有數百筆更新，要在第一次產生完整資料時確認。
- 現有 `output/` 那一批的參數不同，要用新參數重新產生。
