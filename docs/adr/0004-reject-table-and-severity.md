# 0004 Reject 表：規則 × 資料、分嚴重度、先檢查品質再選版本

- 狀態：accepted（2026-10-16）

## 背景

AGENTS.md 規定違反品質規則的資料要寫入 reject 表，grain 是「規則 × 資料」，但沒有說違規的資料要不要從 Silver 排除。

完整的 Synthea 資料很乾淨：關聯斷掉、必填缺值、重複 id 都是 0 筆。唯一天然的問題是 Observation 的代碼格式，共 1,288 筆：1,196 筆眼壓把 SNOMED 代碼 `41633001` 標成 LOINC 系統，92 筆是 Synthea 的佔位代碼 `X9999-0`。這些資料的數值本身沒問題。

## 選項

**違規資料要不要排除：**

- **A. 分兩級**：`error` 擋下，不進 Silver；`warn` 照樣進 Silver，同時寫 reject 紀錄。
- **B. 全部擋下**：任何違規都不進 Silver。
- **C. 全部只記錄**：任何違規都照樣進 Silver。

**品質檢查和選最新版本的順序：**

- **先檢查品質，再從通過的版本中選最新。**
- **先選最新，再檢查品質。**

## 決定

- 選 A。表名維持 `reject`，加上 `severity` 欄位。一筆 reject 紀錄的意思是「一筆資料違反一條規則」，不一定代表資料被擋下。
- 先檢查品質，再從通過的版本中選最新。
- 一筆 reject 紀錄由（規則, 批次, 資源類型, 行號）唯一識別。用行號而不是 id，因為 id 本身可能缺值。
- 「參照的資料不存在」會連鎖：Encounter 被擋下，指向它的 Condition 也會因為找不到 Encounter 被擋下，兩筆各記各自違反的規則。

## 理由

- B 會讓 1,288 筆數值正確的 Observation 消失，只因為代碼標錯系統，代價太高。
- C 會讓沒有 id、參照斷掉的資料進入 Silver，下游的關聯和計數都會出錯。
- 先檢查品質再選版本，規則最好解釋：「只有合格的資料才有資格成為最新版本」。這也和跨批次的行為一致：新版本被擋下時，Silver 保留上一個合格版本。

## 後果

- 完整資料跑完，`error` 級的規則都是 0 筆，所以這些規則有沒有效，只能靠 `tests/fixtures/` 的手工資料證明。
- **已知限制**：參照的資料晚一批才到時（例如 Condition 在批次 3 因找不到 Encounter 被擋下，Encounter 到批次 4 才出現），第一階段不會自動回頭重新處理。Synthea 的 Condition 和它的 Encounter 一定在同一批，所以實際上不會發生。
- 重跑同一批時，該批的 reject 紀錄整批取代，不會重複累積。
