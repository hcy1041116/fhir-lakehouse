# 0005 增量方式：Silver 依版本 MERGE，Gold 全量重建

- 狀態：accepted（2026-10-16）

## 背景

AGENTS.md 要求講清楚「增量」指的是哪一種。範圍要求寫入時只更新有變的，而且同一批重跑結果要一致。

| 種類 | 本專案 |
|---|---|
| 抽取增量 | 不做。Synthea 每批都是完整匯出（最近 10 年） |
| 計算增量 | 做。每次只處理新批次的 Bronze 資料 |
| 寫入增量 | Silver 做；Gold 不做 |

## 選項

**Silver 的寫入方式：**

- **A. 依版本 MERGE**：只寫新增的 id，以及版本較新且內容有變的 id。
- **B. 每批全部重算**：每次讀全部批次的 Bronze，重新選最新版本，整張覆寫。
- **C. 只附加**：每個版本都附加一列，查詢時再挑最新。

**Gold 的寫入方式：**

- **全量重建**：每批處理完後，從 Silver 重算整個 Gold 並覆寫。
- **增量 MERGE**：只更新受影響的列。

## 決定

Silver 選 A。比較每個 id 的來源版本和 Silver 現有版本（比較方式見 ADR-0001）：

| 情況 | 動作 |
|---|---|
| Silver 沒有這個 id | 新增 |
| 來源版本比較新或相同，**而且**內容雜湊值不同 | 更新 |
| 來源版本比較新或相同，內容雜湊值相同 | 不寫（未變） |
| 來源版本比較舊 | 不寫（過期） |

Observation 更新時，它的 coding 和 component 明細整組換掉。

Gold 選全量重建。

## 理由

- 版本比 Silver 現有的舊就不寫，所以處理順序不影響結果：在批次 4 之後重跑批次 2，什麼都不會改。
- 版本相同但內容雜湊值不同時也會更新，所以修正攤平邏輯之後，重跑同一批就能套用新邏輯；邏輯沒改的話，重跑什麼都不寫。
- B 最簡單也一定一致，但每一批都要重讀全部歷史，不算增量，也無法展示「只更新有變的」。
- C 保留了歷史，但每個查詢都要自己挑最新版本，容易出錯。歷史版本本來就都留在 Bronze。
- Gold 資料量小，全量重建最簡單，而且 Gold 的結果只取決於 Silver，重跑一定一致。

## 後果

- Silver 只保留每個 id 的最新版本，不保留歷史（不是 SCD2）。要看歷史就查 Bronze。
- 每列都要存版本比較鍵（有效更新時間、批次序號、行號）和內容雜湊值。
- 內容雜湊值只涵蓋業務欄位，不含簿記欄位，否則每次重跑都會被判定為「有變」。
- 要整個重建 Silver，就清空 Silver，再依序重跑所有批次。
