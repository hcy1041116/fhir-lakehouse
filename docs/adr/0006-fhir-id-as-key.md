# 0006 用 FHIR id 當鍵，不用代理鍵

- 狀態：accepted（2026-10-16）

## 背景

星型模型的慣例是替每個維度產生代理鍵（surrogate key）：一個和來源無關的流水號整數，事實表用它來關聯維度。

這個專案有兩個要求會影響這個選擇：

- 同一批重跑結果要一致。
- Gold 每批都全量重建（ADR-0005）。

## 選項

- **A. FHIR id 當鍵**：維度和事實表直接用 Patient、Encounter 的 FHIR id（UUID 字串）。
- **B. 流水號代理鍵**：用 `row_number`、`monotonically_increasing_id` 或 Delta 的 identity 欄位產生整數鍵。
- **C. 雜湊代理鍵**：對 FHIR id 取雜湊值，當成整數鍵。

## 決定

選 A。唯一的例外是日期維度：`date_key` 用 `yyyymmdd` 整數，因為它是直接從日期推出來的，每次都一樣。

## 理由

- **流水號會破壞重跑一致**：`monotonically_increasing_id` 的值取決於資料的分區方式；`row_number` 取決於排序和當時有哪些資料；identity 欄位每次重新寫入都會配新的值，而且本機和 Databricks 的行為也不一樣。Gold 每批都重建，流水號每次都可能重新分配，任何引用舊鍵的查詢或報表都會對不上。
- **FHIR id 本來就適合當鍵**：它是全域唯一的 UUID，跨批次不變，而且 AGENTS.md 已經規定業務鍵用 FHIR resource id。
- **代理鍵的主要好處這裡用不到**：代理鍵最重要的用途，是在 SCD2 裡區分同一個成員的不同版本。這個專案的維度只保留最新版本（SCD1），不需要。
- C 雖然每次結果一樣，但有雜湊碰撞的風險，可讀性也差，在這個資料量下比 A 沒有任何好處。
- A 的代價是用 36 字元的字串做關聯，比整數慢，但在一千多位病人、六萬多次就診的規模下可以忽略。

## 後果

- 如果以後維度改成 SCD2，需要另外加版本鍵，到時候重新評估這個決定。
- 不同來源系統的 id 可能重複。第一階段只有一個來源，不處理；接入第二個來源時要加上來源前綴。
