# 0008 時區固定 UTC，日期取記錄日期

- 狀態：accepted（2026-10-16）

## 背景

Synthea 的時間字串，用的是產生資料那台電腦的時區：大多數是 `+08:00`，有 334 筆 Encounter 是 `+09:00`（台灣早年的夏令時間）。

Spark 把時間字串轉成 timestamp 之後，要取日期時，會用 session 時區換算。本機 Spark 預設是 `Asia/Taipei`，Databricks 預設是 UTC。同一份程式在兩邊算出來的日期，可能差一天。

例如 `2018-03-30T04:31:33+08:00`：

| 取日期的方式 | 結果 |
|---|---|
| 用 UTC 換算 | 2018-03-29 |
| 用 `Asia/Taipei` 換算 | 2018-03-30 |
| 直接取字串上的日期 | 2018-03-30 |

## 選項

- **A. 用 timestamp 依 UTC 換算日期**
- **B. 用 timestamp 依各平台的預設時區換算日期**
- **C. 時區固定 UTC；日期欄位直接取字串上的日期（記錄日期）**

## 決定

選 C。

- 所有環境的 Spark session 時區都在 config 裡固定為 UTC。
- timestamp 欄位照字串上的時差解析，保存正確的絕對時間。
- 日期欄位和 `date_key` 一律用記錄日期，也就是字串的前 10 個字元，不從 timestamp 換算。

## 理由

- 結果和平台無關，本機和 Databricks 算出來一樣。
- 記錄日期就是來源系統記下「這件事發生在哪一天」，最符合業務上的意思。
- A 會讓清晨的就診被算到前一天，「每天的就診數」這類分析會跟著偏移。
- B 的結果取決於在哪個平台跑，違反「不綁定平台」和「重跑一致」。

## 後果

- 解析日期和時間時，都要從原始字串出發，不能把 timestamp 轉成 date。
- 「記錄日期」已經寫進 GLOSSARY.md，所有日期欄位都遵守同一個定義。
